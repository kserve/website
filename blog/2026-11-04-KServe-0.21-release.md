# Announcing KServe v0.21: Direct KEDA Autoscaling, Kernel Cache, Standalone Tokenizer, and Canary Traffic Splitting

*Published on November 4, 2026*

We are excited to announce the release of **KServe v0.21**. This release focuses on autoscaling flexibility, operational hardening, and deeper llm-d integration, with key highlights including:

- **Direct KEDA autoscaling** for LLMInferenceService, with true **scale-to-zero**
- **Kernel Cache** initial code donation with image signature verification
- **Standalone vLLM tokenizer deployment** replacing the UDS tokenizer sidecar
- **Canary traffic splitting** on RawDeployment HTTPRoutes
- **Rollout strategy** controls for GPU-constrained rolling updates
- **LocalModelCache support for LoRA adapters**
- **`oci+fetch://`** KServe-side OCI image pull and **ModelScope** (`modelscope://`) storage support
- **TLS hardening**: cluster TLS profile flags, hot reload of rotated certificates, and TLS for transformers
- **Python 3.13** support and **Go 1.26** upgrade

## 🚀 LLMInferenceService Enhancements

### 📈 Direct KEDA Autoscaling and Scale-to-Zero

Until now, KEDA-based scaling on LLMInferenceService was only available through the Workload Variant Autoscaler (WVA) path. KServe v0.21 adds a **direct KEDA path** via the new `spec.scaling.keda` field ([#5839](https://github.com/kserve/kserve/pull/5839)), letting users define their own KEDA triggers (CPU, memory, custom Prometheus queries, etc.) without WVA. The controller creates the `ScaledObject` from the user-defined triggers. `spec.scaling.keda` and `spec.scaling.wva` are mutually exclusive, and decode/prefill workloads must use the same scaling mode.

```yaml
spec:
  scaling:
    minReplicas: 1
    maxReplicas: 4
    keda:
      idleReplicaCount: 0
      triggers:
        - type: prometheus
          metadata:
            serverAddress: http://prometheus.monitoring:9090
            query: sum(vllm:num_requests_waiting{namespace="my-ns"})
            threshold: "5"
```

In addition, `idleReplicaCount: 0` is now accepted for both the WVA-mediated and direct KEDA paths ([#5996](https://github.com/kserve/kserve/pull/5996)), enabling **true KEDA scale-to-zero**. `triggerAuthName` can now also be used without `authModes` ([#6004](https://github.com/kserve/kserve/pull/6004)).

### 🔤 Standalone vLLM Tokenizer Deployment

The UDS tokenizer sidecar inside the scheduler pod has been replaced by a **standalone tokenizer Deployment and Service** running vLLM's `/v1/completions/render` endpoint over HTTP ([#5712](https://github.com/kserve/kserve/pull/5712)). This follows the llm-d router v0.9.0+ architecture and enables independent scaling, lifecycle management, and health checking of the tokenizer.

The monolithic `precise-prefix-cache-scorer` plugin is decomposed into the new 3-plugin pipeline (`token-producer` + `precise-prefix-cache-producer` + `prefix-cache-scorer`). Existing configurations are migrated automatically with a deprecation warning event, and a new `TokenizerReady` condition reports the tokenizer status.

### 🔄 Rollout Strategy for Rolling Updates

A new `rolloutStrategy` field ([#5916](https://github.com/kserve/kserve/pull/5916)) lets users configure `maxUnavailable` and `maxSurge` for both single-node Deployments and multi-node LeaderWorkerSets, including prefill workloads. This enables rolling updates on **GPU-constrained clusters** without spare hardware, or faster rollouts with additional surge capacity:

```yaml
spec:
  rolloutStrategy:
    maxSurge: 0
    maxUnavailable: 1
```

### 💾 LocalModelCache for LoRA Adapters

LoRA adapter URIs can now be served from **LocalModelCache** and **LocalModelNamespaceCache** ([#5690](https://github.com/kserve/kserve/pull/5690)). Cached adapters are mounted from PVCs instead of being downloaded at pod startup, independently of whether the base model is cached. Cache deletion is blocked while an LLMInferenceService references a cached adapter.

### 🧭 Scheduler (EPP) Configuration as Presets

The default EndpointPicker configuration is now shipped as **LLMInferenceServiceConfig presets** instead of hardcoded strings ([#5921](https://github.com/kserve/kserve/pull/5921)), updated to the latest llm-d router plugins. Two presets mirror the llm-d guides: an optimized baseline profile and a prefill/decode disaggregation profile. Rendered config templates are now also **validated through the admission chain** before any child resources are created ([#5918](https://github.com/kserve/kserve/pull/5918)).

### 🔗 Working KV Transfer for Prefill/Decode

Prefill/decode disaggregated deployments now get a **NixlConnector** injected automatically (`kv_producer` on prefill, `kv_consumer` on decode) when no other `--kv-transfer-config` is set ([#6027](https://github.com/kserve/kserve/pull/6027)). Previously, decode silently recomputed the prompt KV produced by prefill. User-supplied configuration still takes precedence.

- **Migration to new llm-d metrics flags** and the `metrics-data-source` plugin ([#5877](https://github.com/kserve/kserve/pull/5877), [#5930](https://github.com/kserve/kserve/pull/5930))
- **EndpointPickerConfig apiVersion migration** ([#5774](https://github.com/kserve/kserve/pull/5774))
- **LoRA adapter validation** and disambiguation of colliding mount paths ([#6092](https://github.com/kserve/kserve/pull/6092), [#6085](https://github.com/kserve/kserve/pull/6085))
- **Traffic splitting group fixes** for stopped and terminating members and pool matching ([#5847](https://github.com/kserve/kserve/pull/5847), [#6149](https://github.com/kserve/kserve/pull/6149), [#6156](https://github.com/kserve/kserve/pull/6156))

## 🧠 Kernel Cache

KServe v0.21 includes the **initial code donation of Kernel Cache** ([#5590](https://github.com/kserve/kserve/pull/5590)), starting with the MCV CLI tool and API for building kernel cache container images, extracting caches, and running preflight checks. Pre-compiled GPU kernel caches can significantly reduce model server startup times by avoiding repeated kernel compilation.

To ensure that only trusted kernel caches are used, this release also introduces a **security verification framework** ([#6099](https://github.com/kserve/kserve/pull/6099)), **cert-mode signature verification** ([#6103](https://github.com/kserve/kserve/pull/6103)), and a **signing contract** ([#6118](https://github.com/kserve/kserve/pull/6118)).

See the [Kernel Cache documentation](/docs/next/model-serving/generative-inference/modelcache/kernel-cache/overview) to get started.

## 🔧 InferenceService and Platform Improvements

### 🐦 Canary Traffic Splitting on RawDeployment HTTPRoutes

Building on the canary rollout support introduced in v0.20, HTTPRoutes in RawDeployment mode now carry **weighted backend refs** for canaries ([#5912](https://github.com/kserve/kserve/pull/5912)). The stable predictor receives the remaining weight after all canary percentages, and HTTPRoute names and hostnames remain stable through promotion — only backend refs change:

```yaml
# HTTPRoute: my-model-predictor (20% canary)
backendRefs:
  - name: my-model-predictor
    weight: 80
  - name: my-model-v2-predictor
    weight: 20
```

Canary traffic is now **gated on readiness** to prevent transient 503s ([#5984](https://github.com/kserve/kserve/pull/5984)), canary weights are restricted to predictor rules ([#5944](https://github.com/kserve/kserve/pull/5944)), and orphaned autoscaler and OpenTelemetry resources are cleaned up on promotion ([#5899](https://github.com/kserve/kserve/pull/5899)).

### 🔍 InferenceService Tracing API

InferenceService now has an optional top-level **`spec.tracing`** field ([#6108](https://github.com/kserve/kserve/pull/6108)), aligned with the LLMInferenceService tracing API. Setting `tracing: {}` applies defaults (`otlp` exporter to `http://otel-collector:4317`, `parentbased_traceidratio` sampler at `0.05`), with admission validation for sampler names and exporter endpoints. This release establishes the API contract; workload injection will follow in a future release.

### 📦 Storage Enhancements

- **`oci+fetch://`** ([#5739](https://github.com/kserve/kserve/pull/5739)) — Step 3 of the OCI storage harmonization roadmap ([#4083](https://github.com/kserve/kserve/issues/4083)). An init container pulls the OCI image with oras-py and extracts the `/models/` subtree, without depending on container runtime features. This works on older Kubernetes versions and restricted environments, and supports private registries through `imagePullSecrets`.
- **ModelScope support** ([#5330](https://github.com/kserve/kserve/pull/5330)) — download models directly from [ModelScope](https://www.modelscope.cn) using the `modelscope://` URI scheme, mirroring the existing Hugging Face integration:

  ```yaml
  storageUri: "modelscope://qwen/Qwen2-0.5B-Instruct"
  ```

- **IBM Power (ppc64le) support** for the storage initializer ([#5235](https://github.com/kserve/kserve/pull/5235))
- **AWS SDK migrated from v1 to v2** in the agent ([#5438](https://github.com/kserve/kserve/pull/5438))

### 🎯 DRA Support for ServingRuntime

ServingRuntime and ClusterServingRuntime now support pod-level **`resourceClaims`** for Dynamic Resource Allocation ([#5828](https://github.com/kserve/kserve/pull/5828)). Runtime defaults are merged with InferenceService predictor overrides, so DRA-backed InferenceServices can be scheduled correctly.

### 🧩 Independent CRD Installation

CRD management has been restructured so CRDs can be **installed independently** from the controllers with proper cert-manager webhook annotations ([#5843](https://github.com/kserve/kserve/pull/5843)). All existing installation methods continue to work.

### Additional Enhancements

- **Python 3.13 support** ([#5897](https://github.com/kserve/kserve/pull/5897))
- **AutoGluon server** injects a synthetic item ID for two-column time series inputs ([#6009](https://github.com/kserve/kserve/pull/6009))
- **Headless InferenceService status URL** now reports the correct port ([#5968](https://github.com/kserve/kserve/pull/5968))

## 🔒 Security Improvements

### TLS Hardening

- **Cluster TLS security profile integration** ([#5791](https://github.com/kserve/kserve/pull/5791)) — new `--tls-min-version` and `--tls-cipher-suites` flags for webhook and metrics servers across all KServe controllers, defaulting to hardened TLS 1.2. The `--enable-http2` flag has been removed from the llmisvc controller.
- **Rotated TLS certificates are reloaded** by the model server without a restart ([#6106](https://github.com/kserve/kserve/pull/6106)).
- **TLS for transformers** via the `KSERVE_TLS_CERT_FILE` and `KSERVE_TLS_KEY_FILE` environment variables, enabling end-to-end TLS ([#6045](https://github.com/kserve/kserve/pull/6045)), plus CA bundle injection for `httpx` ([#5932](https://github.com/kserve/kserve/pull/5932)).
